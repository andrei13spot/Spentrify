# Spentrify Cheat Sheet (Presentation-Ready)

## 1. Project Overview

### What the project is
- Spentrify is a **mobile-first spending tracker** built with **Expo (React Native)** and a **Node.js + Express + SQLite** backend.
- It supports **manual expense logging**, **SMS-based transaction detection** on Android, **goals/budgets**, **analytics dashboards**, **AI insights**, **notifications**, and **CSV exports**.

### What problem it solves
- Helps users **track daily expenses**, **understand spending habits**, and **stay within budgets**.
- Automates detection of financial transactions from **bank SMS** (Android).
- Provides **actionable insights** and **exportable reports** for taxes (ITR) and reimbursements.

### High-level system architecture
- **Frontend (Mobile App)**: Expo + React Native + Expo Router + Zustand + Axios.
- **Backend (API Server)**: Express.js + SQLite + custom services for encryption, analytics, AI insights, exports.
- **Database**: SQLite with encrypted sensitive fields.
- **APIs**: REST endpoints under `/api/*` for auth, transactions, insights, analytics, exports, notifications, goals.

## 3. Code Explanation (Simple, Step-by-Step)

### Authentication (Login/Signup)
1. **Login screen** (`app/index.tsx`) collects email/password.
2. Calls `AuthContext.loginWithEmail()` → POST `/api/auth/login`.
3. Backend (`authController.js`) validates and uses `authService.authenticateUser()`.
4. Email is **encrypted in DB**; password is **hashed**.
5. Frontend stores user in AsyncStorage and navigates to tabs.

### Transactions (Manual Add)
1. User opens **Add** tab (`app/(tabs)/add.tsx`).
2. Form builds payload with amount, category, date.
3. Calls `DataContext.addTransaction()` → POST `/api/transactions`.
4. Backend `transactionsController.createTransaction()`:
   - Validates user.
   - Encrypts amount, merchant, description via `transactionsService`.
   - Inserts into `Transactions` table.
   - Creates a notification.
5. Frontend refreshes list and shows confirmation modal.

### Transactions (SMS Detection on Android)
1. `TransactionListener` runs globally in `app/_layout.tsx`.
2. It listens to Android SMS via `react-native-android-sms-listener`.
3. On new SMS, it POSTs raw SMS to `/api/transactions/detect`.
4. Backend `categoriesService.parseNotification()` extracts:
   - amount
   - merchant
   - category suggestion
5. Frontend opens `/pop-up` with detected data.
6. User confirms category → transaction saved.

### Goals (Savings)
1. Goals UI uses Zustand store (`goals-store.ts`).
2. CRUD calls `/api/goals` endpoints.
3. Backend `goalsService` encrypts goal name/amounts in `SavingsGoals` table.

### Insights (AI + Rules)
1. Insights screen (`app/(tabs)/insights.tsx`) can run in:
   - `gemini` mode
   - `rules` mode
2. It POSTs `/api/insights/generate` with `mode`.
3. Backend `aiInsightsService.generateInsights()`:
   - Gemini summary (if API key is set).
   - ML/statistical insights via `mlInsightsService`.
   - Fallback rule-based insights.
4. Insights are stored in `AI_Insights` table.
5. Insight detail screen (`app/insight/[id].tsx`) requests:
   - `/api/insights/detail` for Gemini-enhanced breakdowns.

### Analytics (Dashboard)
1. Home screen fetches:
   - `/api/analytics/by-category`
   - `/api/insights`
2. Backend `analyticsService` decrypts amounts and aggregates totals.
3. Frontend renders charts and insight card.

### Exports (CSV)
1. Exports screen (`app/exports.tsx`) calls:
   - `/api/exports/itr`
   - `/api/exports/reimbursement`
2. Backend `exportService` decrypts transactions and generates CSV strings.
3. Frontend shows preview and lets user download/share.

### Notifications
1. Notifications are stored in the backend table `Notifications`.
2. UI (`app/notifications.tsx`) fetches list and supports:
   - Delete single: `DELETE /api/notifications/:id`
   - Clear all: `DELETE /api/notifications`

## 4. Application Flow (End-to-End)

### Example Flow: Add Transaction (Manual)
1. **User action**: taps "Add Transaction".
2. **Frontend**: validates inputs → `POST /api/transactions`.
3. **Backend**: encrypts data → inserts into SQLite.
4. **Database**: `Transactions` row created.
5. **Processing**: backend creates a `Notifications` record.
6. **Response**: success → frontend refreshes dashboard.
7. **Error handling**:
   - Validation errors return 400 with message.
   - DB failure triggers error middleware (500).
   - Frontend shows error modal.

### Example Flow: SMS Detection (Android)
1. **User action**: receives bank SMS.
2. **Frontend**: SMS listener reads message.
3. **Backend**: `/api/transactions/detect` parses it and suggests category.
4. **Frontend**: popup screen asks user to confirm category.
5. **Backend**: save confirmed transaction.
6. **Database**: encrypted transaction stored.

### Example Flow: View Insights
1. **User action**: opens Insights tab.
2. **Frontend**: calls `/api/insights/generate`.
3. **Backend**: ML analysis + Gemini summary.
4. **Database**: AI_Insights updated.
5. **Frontend**: fetches `/api/insights` and renders cards.

## 5. Database Explanation

### Database Type
- **SQLite** (local file-based database).
- DB path: `backend/.env` → `DB_PATH=./spentrify.db`.

### Tables & Fields

#### `Users`
- `user_id` (PK)
- `email_encrypted`
- `passcode_hash`
- `full_name`
- `phone`
- `is_email_verified`
- `is_cloud_sync_enabled`
- `last_sync_timestamp`
- `created_at`

**Why it exists**: Stores account and preference data.

#### `Categories`
- `category_id` (PK)
- `category_name`
- `is_itr_deductible`
- `icon_identifier`
- `created_at`

**Why it exists**: Standard category list for consistent filtering and exports.

#### `Transactions`
- `transaction_id` (PK)
- `user_id` (FK → Users)
- `category_id` (FK → Categories)
- `amount_encrypted`
- `merchant_name_encrypted`
- `description_encrypted`
- `transaction_date`
- `source_type`
- `reference_number`
- `is_manual`
- `is_reimbursable`
- `receipt_image_path`
- `created_at`

**Why it exists**: Core spending records (encrypted).

#### `AI_Insights`
- `insight_id` (PK)
- `user_id` (FK → Users)
- `insight_type`
- `message`
- `is_read`
- `detail_json`
- `detail_generated_at`
- `created_at`

**Why it exists**: Stores generated AI insights for the user.

#### `Notifications`
- `notification_id` (PK)
- `user_id` (FK → Users)
- `title`
- `message`
- `is_read`
- `created_at`

**Why it exists**: App-level alerts for activity.

#### `SavingsGoals`
- `goal_id` (PK)
- `user_id` (FK → Users)
- `name_encrypted`
- `target_amount_encrypted`
- `current_amount_encrypted`
- `deadline_date`
- `status`
- `created_at`

**Why it exists**: Savings goals with encrypted amounts.

### Relationships
- **Users → Transactions**: one user has many transactions.
- **Users → SavingsGoals**: one user has many goals.
- **Users → AI_Insights**: one user has many insights.
- **Users → Notifications**: one user has many notifications.
- **Categories → Transactions**: one category can have many transactions.

### CRUD Patterns
- **Create**: Insert encrypted fields before saving.
- **Read**: Decrypt fields in services before returning to frontend.
- **Update**: Encrypt updated fields; keep only changed columns.
- **Delete**: Hard delete by ID + user ID.

### Backend Interaction
- All data reads/writes go through services in `backend/services/*`.
- Controllers validate inputs and return JSON responses.

### Note on Budget Tables (Implementation Detail)
- Some budget logic references a `Budgets` table (e.g., `budgetsService`, `Budgets` routes).
- `connection.js` does **not** create a `Budgets` table.
- Current goals are stored in `SavingsGoals`.
- This is important if asked why budgets behave differently in practice.

## 7. Security & Configuration

### Environment Variables (backend/.env)
- `PORT`: backend server port (default 3000).
- `DB_PATH`: SQLite database file path.
- `ENCRYPTION_KEY`: 32-byte hex key for AES-256-GCM.
- `GEMINI_API_KEY`: Gemini API key (optional).
- `GEMINI_MODEL`: Gemini model name (optional, default `gemini-2.0-flash`).

### Frontend Environment
- `EXPO_PUBLIC_API_URL`: overrides API base URL for app.

### Authentication
- Email + password login/signup.
- Passwords are **hashed** (bcrypt if available, SHA-256 fallback).
- Email stored **encrypted** in DB.

### Authorization
- Uses `user_id` query/body parameters (no JWT yet).
- Requests are user-scoped by `user_id`.

### Why these are important
- Encryption protects sensitive financial data if DB is accessed.
- Environment variables prevent secrets from being hardcoded.
